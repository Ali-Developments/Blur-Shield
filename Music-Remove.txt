User Flow — High Level

User taps the "Remove Music" toggle in the YouTube platform view.
The app (React Native / Expo) resolves the currently-open YouTube page → computes a public URL for the video.
The RN client POSTs the YouTube URL to the backend: POST /api/audio/youtube-jobs → receives jobId.
The RN client polls GET /api/audio/youtube-jobs/{jobId} until status becomes "done".
When done, RN constructs /api/audio/youtube-jobs/{jobId}/result, downloads the MP3 to the app cache, creates an Audio.Sound from the local file, calls playAsync(), and only after playback has started injects JS into the WebView to mute the original <video>/<audio> element(s).
Result: user hears the cleaned (vocals-only) native audio while the WebView continues showing the video visually.

3) WebView — role, mute strategy, comms

Why WebView:

The WebView embeds the remote platform (YouTube) to show the original video UI and allow user interaction (seek, controls, comments, etc.). The WebView is required for the visual experience.
Why not do separation in page:

Browsers block cross-origin access to media elements (no MediaElementAudioSource from cross-origin media → either throws or outputs silence). You cannot run client-side WebAudio separation on YouTube due to CORS.
How the app integrates instead:

Server-side separation produces a cleaned audio stem.
The RN app plays the cleaned stem natively and the WebView is muted (so visuals continue).
The in-page script only mutes/unmutes and signals readiness via postMessage.
What buildVocalFilterJS() does:

File: blurScript.ts
Returns a JS snippet that:
Finds <video> and <audio> elements that are playing and:
Saves original volume/muted state on dataset.bsOrigVolume/bsOrigMuted

Marks element with dataset.bsVocalReduced
Installs a MutationObserver and periodic scan to mute elements that start playing later
Posts bs_audio_ready via window.ReactNativeWebView.postMessage(...) to notify RN when the in-page helper is active

Crucial note in the file (commented): it does NOT attempt any in-page source separation. Mute-only by design (server-side separation is used).

4) API Endpoints (requests & responses, purpose)

All endpoints are under /api/audio as served by youtube.ts:

POST /api/audio/youtube-jobs

Client request: JSON body containing videoId or videoUrl.
Server response: 200 { jobId } on acceptance; 400 for bad input; 503 if Python worker unavailable or worker script missing.
Purpose: accept work request, queue it, spawn worker, return jobId immediately for client polling.
GET /api/audio/youtube-jobs/:id

Client request: no body.
Server response: 200 JSON describing job:
Purpose: client/polling to poll progress & final status.
GET /api/audio/youtube-jobs/:id/result

Client request: supports Range header; used by FileSystem.downloadAsync or audio players that seek.
Server response: 200 (full file) or 206 (range) with Content-Type: audio/mpeg.
Purpose: stream the processed MP3 for download and playback.
5) Backend — exact internal behavior when a request reaches Express

Job lifecycle store:

In-memory Map<string, YoutubeJob> (jobs in routes/youtube.ts).
Jobs include statusFile (path polled) and resultPath (final MP3).
On POST /youtube-jobs:

Validate input; resolve Python via resolvePython().
Resolve script path (youtube_separator.py), create unique jobId, statusFile path and outputPath.
Save a YoutubeJob object (status queued) in jobs.
Immediately res.json({ jobId }).
Spawn worker process with spawn(python, [scriptPath, '--youtube-url', youtubeUrl, '--output', outputPath, '--status-file', statusFile]).
Mark job as processing.
Set up a server-side interval (1.5s) to read the statusFile JSON (written periodically by the worker) and update job.stage, job.progress, job.message.
Collect stdout/stderr into buffers; on process close:
Parse final JSON from stdout last line; if result.success && output exists → set job.status = 'done', job.resultPath = outputPath.
Otherwise mark job.status = 'error' and put error message on job.
GET job status endpoint simply returns the job JSON view.

GET result endpoint:

If job.status !== 'done' or job.resultPath absent → 404.
If file expired (no longer exists) → 410.
Supports range requests and streams file with proper headers.
Job pruning:

Background interval prunes jobs and files older than 60 minutes.

10) Implementation review — strengths and weaknesses

Strengths

Correct architectural division: in-WebView muting + server-side separation is the only practical approach on cross-origin pages like YouTube.
Clear contract: client posts URL, server returns jobId immediately, client polls. This decouples long-running work from HTTP request lifecycle.
Status-file IPC: Python writes JSON to a status file which Express polls; simple and robust for progress visibility.
Result streaming supports ranges (seek support).
Native playback via expo-av enables reliable background playback and better audio control than WebView.
Weaknesses / Risks / Observed Issues

Networking assumptions: getApiOrigin() must be correct for physical Android devices (common pitfall: localhost vs LAN IP). If mis-set, app will never reach the backend — this is a runtime issue, not algorithmic.
Single-server spawn model:
CPU heavy: ONNX MDX-Net on CPU is very slow (minutes per track); server spawns workers per request → poor concurrency and resource exhaustion on a single cheap host.
No job queue persistence: jobs stored in-memory Map → server restart loses jobs and files.
Worker stdout parsing:
routes/youtube.ts buffers stdoutBuf and then tries to parse the final JSON line. If the worker emits unexpected logs or large outputs, the JSON parse can fail or be truncated; this can turn completed jobs into error states.
Status-file race conditions:
Server polls statusFile every 1.5s; worker removes statusFile on exit. If the server misses the last write before worker exit, the client might see stale progress or short gap.
Temporary file handling:
Worker creates temp workdir and removes it on exit. If Express tries to stream file after worker deleted workdir → missing file. But Express stores resultPath and only marks job done if fs.existsSync(outputPath) at close time, so usually safe; however pruning and cleanup windows must be observed.
Selection heuristics:
audio_output_selector is heuristic-based (name tokens + energy). It may mis-select stems for models that name outputs unexpectedly.
Client-side playback sync:
Native audio and WebView visuals may drift. The code tries to sync with messages, but perfect A/V sync is hard (seek/pause events need careful propagation).
Expo AV / FileSystem concerns:
FileSystem.downloadAsync can fail on Android if paths/permissions are incorrect; Audio.Sound.createAsync expects  or content:// URIs in certain Android versions.
Background download + playback reliability depends on Android SDK / Expo client behavior.
Security & scaling:
Serving large MP3s from tmp can expose file paths; no auth on the result URL besides ephemeral jobId. If jobId is guessable, access risk exists (but jobId is a UUID).
UX delay:
Model runs are slow on CPU — real-time removal is impractical on common dev hosts. UX must reflect expected delay (activating spinner, progress messages).
Duplication / Complexity

Two very similar platform components exist: [id].tsx and platform-id.tsx — logic is duplicated.
Several small helpers (blur/music script variants) and duplicated logging paths exist across files.
Possible race / sync problems

If sound.playAsync() is called but WebView JS injection fails (or vice versa), user may hear both streams or none. The code tries to inject mute only after play, but injection failures are fatal fallbacks.
Polling intervals (1.5s) mean a small delay before client learns job completion; acceptable but not instant.
11) Final capability assessment — can this architecture achieve the desired behavior?

Desired behavior: press Remove Music → background music removed, speech preserved, video continues visually.

Fundamentally: YES — the architecture is correct for the target constraint (cross-origin YouTube media). The only practical approach is server-side separation + native playback + webview mute.
The chosen model (Kim_Vocal_2.onnx MDX-Net) is appropriate for extracting vocals.
The end-to-end flow (POST → worker → result → download → native playback → mute) maps cleanly to the desired UX.
Where it can fail in practice (but not due to architectural design):

Networking: If the app cannot reach the server from the device (wrong API_BASE), the feature fails immediately (this is an operational/configuration issue we previously inspected).
Performance & latency: on CPU-only hosts, MDX-Net is slow. This yields long wait times — functional, but poor UX and scaling problems.
Selection errors: the heuristic selection may occasionally pick a wrong stem (e.g., low-energy vocals or mislabeled outputs) resulting in silent or poor-quality audio.
Sync edge-cases: small A/V drift, or race where native audio starts slightly off relative to video leading to perceptible lip-sync issues.
Robustness: worker stdout parsing or status-file races could cause false errors if worker logs are noisy or truncated.
Bottom line: architecture is fundamentally correct and practically viable, but success depends on operational factors (correct API address on device, sufficient backend resources, robust process stdout/status handling).
